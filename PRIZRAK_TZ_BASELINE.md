# Prizrak v11 — baseline spec (from user-approved architectural answers)

Этот документ фиксирует **базовый контракт поведения** для следующей стабильной версии.
Основание: ответы пользователя в формате ТЗ/архитектуры (20 пунктов).

## 1) Приоритетные ТФ
- Основные рабочие: **M15 / H1**.
- Структурный HTF по умолчанию: **H4** (`htf = "240"`).
- D1 поддерживается как дополнительный режим.

## 2) Приоритетные рынки
- Приоритет: crypto / stocks / futures (где объём более пригоден для stop-volume).
- Forex/indices поддерживаются, но качество volume может быть хуже.

## 3) Разная логика по рынкам
- Базово: **единая логика без ветвления по типу рынка**.
- Допустима только параметрическая адаптация (не отдельные алгоритмы).

## 4) Определение “истинного флэта”
- Для strict-compat: **процентный диапазон** (как в текущем контракте), не ATR-only.

## 5) Минимальный “возраст” флэта
- Определяется окном `max_flat_bars` + условиями касаний (`min_touches`, `min_touches_side`).

## 6) Подтверждение выхода из флэта
- Комбинированно:
  - `high/low` для early/true break,
  - `close` + счётчик баров для weak-confirm выхода.

## 7) Дефолт режима POC-цены
- Для baseline: **HLC3** (совместимость с исходным `.pine`).
- Варианты остаются: CLOSE / HL2 / HLC3 / VWAP.

## 8) Когда POC “мёртвый”
- Базово: после `N` тестов (`poc_dead_tests`).
- Дополнительно: может деактивироваться при TRUE-выходе родительского флэта.

## 9) Разделение SV POC и обычного POC
- В baseline одинаковые правила жизненного цикла (старение/смерть), различие только по метке/типу.

## 10) Stop-volume внутри флэта
- По умолчанию: **разрешён внутри флэта** (`stop_detect_inside_flat = true`).

## 11) CHOCH и ретест
- TRUE-сигнал требует ретест при включённом флаге `choch_need_retest=true`.
- EARLY может активироваться без ретеста.

## 12) Как CHOCH блокирует входы
- Для strict-compat: CHOCH блокирует генерацию **всех** сетапов во время active/pending.

## 13) RSI/MACD фильтры
- Схема: мягкое подтверждение + запрет противоречащих паттернов.
- Не сводить грубо к простому AND/OR без отдельного решения.

## 14) Контртренд-входы
- Базовый дефолт: `allow_counter = false`.
- RR gate включён по умолчанию.

## 15) RR-gate
- Проверка по **TP main/ext**, не по TP1.

## 16) TP1 -> BE
- Перенос в BE выполняется всегда при достижении TP1 (в рамках текущего контракта).

## 17) Конфликт BUY/SELL
- В strict-compat при одновременном конфликте приоритет BUY (как в текущем тернарном выборе).

## 18) Обязательные визуальные слои
- Базовый набор: рабочий уровень + POC линии + level zones + RR history.
- Остальные слои остаются опциональными.

## 19) Совместимость с input-полями
- Для стабильного релиза: **полная обратная совместимость** (имена/порядок/options/дефолты).

## 20) Критерий “полностью исправного” релиза
- Для strict-compat:
  1. Скрипт компилируется без ошибок.
  2. Сигналы/объекты сопоставимы со старой версией.
  3. Изменения визуала не ломают геометрию/жизненный цикл объектов.
- Любые алгоритмические улучшения — отдельный evolution-релиз.

---

## Actionable implementation mode
- Режим по умолчанию: **Strict-compat**.
- Любые отклонения от пунктов выше должны быть явно перечислены в changelog до релиза.
